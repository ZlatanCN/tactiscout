# TactiScout 对话式球探 MVP

Status: in-progress
Labels: ready-for-agent

## Problem Statement

TactiScout 当前把招募需求压成结构化表单，再用固定筛选和启发式公式生成候选名单。这与球探实际表达需求的方式不符：用户往往只会说“找凯恩的替代者”或“给巴萨找个新后卫”，Agent 需要先理解任务、调查阵容和角色能力，再决定下一步调用什么数据工具，或在高影响信息缺失时向用户追问。推荐还必须说明证据和数据覆盖，避免把简单代理指标包装成完整球员能力。

## Solution

把工作台改成对话式球员评估与推荐流程：用户从一句自然语言开始，LangGraph 在共享案件状态中组织可用阵容/球员调查、能力画像、候选发现、深入评估和证据审核。Agent 先用工具查清现有数据，再判断是否需要问一个会改变评估方向的问题；用户回答或修正需求后，工作流继续调查。结果围绕目标角色比较球员的可观测能力、适配理由、样本风险和未知项。用户仍可保存招募计划和最近结果快照、比较候选人并重新分析；已保存计划继续放在浏览器 localStorage。

LLM 是调研协调者：它从自然语言建立初步任务假设，查看工具证据后动态选择下一步调查，并判断是否需要向用户澄清。球队/球员事实必须来自可追溯的数据工具；统计计算和明确的硬条件由确定性代码把关。LLM 不能把推断冒充成用户确认，不能编造球员事实或把缺失数据补成确定结论。

## User Stories

1. 作为球探，我想用一句自然语言说明要解决的阵容问题，以便不用先填写一长串筛选字段。
2. 作为球探，我想让 Agent 先检查可用的阵容与球员表现证据，再提出下一步问题，以便它不会把已有的调查工作推回给我；数据源不支持当前阵容核实时，它应明确说明限制。
3. 作为球探，当“替代者”“新后卫”等说法存在多个合理解释时，我想看到 Agent 说明当前理解，并只在答案会改变推荐时向我追问。
4. 作为球探，我想在回答追问、补充预算偏好或改变方向后继续同一招募案件，以便候选研究能基于此前调查推进。
5. 作为用户，我想看到 Agent 推导的目标能力画像，并通过补充对话修正它，以便我能校正角色理解。
6. 作为用户，我想看到每项重点能力对应的可观测指标和对比组，以便理解候选评估依据。
7. 作为用户，当数据样本或比较组不足时，我想看到明确标注，以便不把数据缺口误认为球员短板。
8. 作为用户，我想按目标角色的可观测能力证据评估和比较候选球员，以便推荐主要来自表现与职责适配，而非机械筛选。用户主动提出的位置或年龄偏好可作为辅助条件。
9. 作为用户，我想查看每名候选人的每 90 分钟数据、出场样本、来源、赛季和位置，以便判断比较是否公平。
10. 作为用户，我想查看每项适配信号背后的统计依据和风险，以便区分数据事实与启发式解释。
11. 作为用户，我想知道证据覆盖反映的是可用指标和样本情况，以便不把它理解为推荐正确概率。
12. 作为用户，我想看到 Agent 建议优先继续考察的候选顺序，以便决定下一步研究对象；此顺序不是经离线验证的客观能力排名。
13. 作为用户，我想选择 2–3 名候选人并排比较关键统计、赛事/赛季、数据来源、样本和风险，以便进一步评估差异；首版不展示缺乏数据定义支持的有球/无球适配分。
14. 作为用户，我想把一次需求和最近的分析结果保存成招募计划，以便离开页面后继续查看。
15. 作为用户，我想重命名、编辑和删除自己的招募计划，以便整理本地工作空间。
16. 作为用户，我想手动重新分析一个已保存计划，以便获取当前数据对应的新结果。
17. 作为用户，我想在重新分析前继续查看上一份分析快照，并在完成后用新快照替换，以便刷新失败时不丢失旧结果。
18. 作为演示者，我想在没有本地真实数据集时使用标明为虚构的演示数据，以便完整展示交互流程。
19. 作为使用 StatsBomb Open Data 的用户，我想看到数据集范围、统计代理指标和年龄限制，以便理解结果的适用边界。
20. 作为用户，我想用简体中文完成主要工作流，以便界面语言一致、易读。

## Implementation Decisions

- 保持全 TypeScript：React 工作台、Fastify 服务端和 LangGraph 分析工作流。
- 以 LangGraph StateGraph 表达对话式招募案件，而不是固定筛选流水线。共享状态记录原始需求、当前理解、可追溯调查证据、推导出的能力画像、已确认偏好、待回答问题、候选池和当前阶段。
- Agent 按需调用球队/球员/比赛数据工具。调研 Agent 和工具执行之间存在真实条件循环；工具结果进入状态后，Agent 才决定继续调查、追问还是提交结论。
- 以能力画像和证据比较作为候选推荐主线。确定性分析计算可复现的比赛指标和样本风险，LLM 负责规划查询、从更广候选中选择后续评估对象、解释证据和呈现取舍，不自行发明分值。候选发现默认不按分钟数或能力做代理排序；位置、年龄等只作为用户明确提出或 Agent 有依据推导的辅助条件，不替代能力评估。
- 只在当前数据无法解决、且答案会明显改变画像或候选方向时追问。使用 LangGraph `interrupt` 暂停，用户回答后通过同一 `thread_id` 恢复案件；问题要少而具体，不把所有可能筛选字段预先变成表单。
- 使用 `@langchain/openai` 的 `ChatOpenAI` 适配兼容 OpenAI 的模型服务。服务端从环境变量读取模型名称、可选兼容服务地址和密钥；密钥不得发送到浏览器。具体模型名由本地配置决定。
- 未配置模型时可保留明确标注的手动分析模式，但不得把它伪装成具备动态工具编排和多轮追问的 Agent。
- 球员能力评估按目标角色选择有球、无球、创造、推进、终结、防守、传球等可观测证据；比较时展示每个维度、对比基准、数据来源/赛季/分钟数及代理限制。不要用当前几条统计公式生成看似精确的总能力分或未经校准的推荐等级。
- StatsBomb 阵容记录缺少对应比赛事件文件时，球员可保留为候选线索，但不把缺失动作当成零，不生成其比赛表现证据或推荐依据；没有传球尝试时不报告传球成功率，并据此计算实际可用指标覆盖。
- 首版聚焦球员能力和角色适配；年龄、预算等不是开场必填项，用户主动提出时才作为辅助偏好。暂不实现非欧、工作许可、注册名额等转会与注册细则，也不根据缺失的财务信息推断俱乐部预算。
- 球队实体可在自然语言中直接提供；仅当实体有歧义时再让用户通过紧凑的可搜索选择控件澄清。位置和职责也不要求用户在开场预填，可由阵容/角色调查推导并标明推断。
- 证据覆盖摘要报告已评估人数、可用指标值/预期指标值、小样本人数和同组比较受限人数。它说明数据可用性与样本覆盖，不是推荐正确率；界面明确称为 `证据覆盖`，避免称为“推荐置信度”。
- 报告逐项展示 Agent 实际用于候选发现的位置、年龄、样本、赛事和赛季条件，并标明这些条件是 Agent 根据对话解释后使用的，允许用户继续纠正；旧版结构化表单迁移时标记为用户确认。
- 比较视图只接受当前候选名单中用户明确选择的 2–3 人，并并排展示完整的已计算指标、同组百分位、赛事/赛季、来源、分钟样本和数据风险。首版不展示缺乏可验证计算口径的有球/无球适配分。
- 每份招募计划包括对话记录、计划名称、创建/更新时间，以及最近一次完整分析报告快照。计划支持创建、打开、补充对话、重命名、删除和手动复核；复核成功后才替换快照。旧版单次分析计划迁移为历史报告。
- 招募计划和报告快照只保存在浏览器 localStorage；第一版没有用户账号、跨设备同步或服务端数据库。存储内容带版本标记，旧格式在读取时迁移并立即写回新版本。
- LangGraph 通过注入式规划器接口隔离模型决策，并用 StateGraph 循环组织结构化动作、球队/候选/评估工具、条件路由、`interrupt` 追问、证据审查和最终报告。除每轮 10 步的总决策上限外，`inspect_team`、方法检索、候选检索、能力评估和球员报告检索分别最多调用 2、2、4、3、2 次；超过单项预算时回到规划器选择其他动作。生产规划器使用 `ChatOpenAI.withStructuredOutput`；未配置模型服务时返回明确错误，不回退到静态筛选。
- 对话 HTTP seam 为 `POST /api/v1/recruitment/cases/:caseId/turns`；前端和 Fastify 共用 Zod 响应契约。`caseId` 映射 LangGraph `thread_id`，用于中断后继续同一案件。
- RAG 拆成两个独立语料：角色/战术方法资料用于需求解析和目标能力画像；球员报告用于候选线索和带来源的定性观察。两类资料保留各自的来源、许可和实体元数据，不能把方法资料当成某名球员的证据。
- 联网搜索用于发现潜在来源；只有来源登记明确允许自动访问、正文持久化和 AI/RAG 处理后，抓取器才可获取正文并写入索引。条款不清楚或用途不允许的正文不得进入索引或模型上下文；可展示的来源链接仍须遵守来源自己的访问与展示条件。
- 检索顺序为：先检索角色/战术方法资料以辅助建立能力画像；完成结构化候选筛选与比赛表现评估后，再检索球员报告补充定性观察。报告引出的新球员可回到候选调查与结构化数据核验环节；LangGraph 为方法检索、结构化评估、报告检索及回查设置明确的工具预算上限。
- 报告观察可影响定性建议与后续考察优先级，但不得直接折算成能力分。可由比赛数据核验的观察应触发结构化核验；无法核验的观察必须保留来源、作者/机构、日期并标为未证实，不得表述为确定球员事实。
- RAG 文档与向量索引首版使用服务端本地持久化，和浏览器 `localStorage` 中的招募计划分开管理；MVP 使用 LanceDB 本地目录。检索结合向量语义、BM25 式关键词相关度和 reciprocal-rank fusion，并先按语料、许可门控与实体元数据过滤。
- 向量生成默认使用服务端本地 Transformers.js embedding provider，模型初选 multilingual E5 ONNX；保留可显式配置的远程 embedding provider 接口，但不能静默把正文发送到第三方。首次使用本地模型需要下载并缓存权重；模型标识/版本属于索引元数据，变更模型需重建向量。
- RAG 与 Agent 评测使用小型标注集，分别检查检索命中、引用/结论是否受证据支持、以及工具选择与追问决策。LLM-as-judge 只能作为辅助；没有可信球探标注时，不宣称推荐排序有客观准确率。
- 第一版使用 `MemorySaver` 保存图的运行时 checkpoint。它可在 API 进程存活期间恢复暂停案件；重启 API 会丢失内部工具状态。浏览器会保存可见对话和报告快照，但这不等于持久化图 checkpoint；尝试恢复丢失的案件时，接口返回明确错误，要求新建案件并重述需求。持久化 checkpoint 后端仍待决策。
- 主要表现数据来源先使用本地 StatsBomb Open Data，并明确说明覆盖的赛事/赛季范围；该数据集不代表完整的当前俱乐部阵容或转会市场。不能从历史比赛阵容推断俱乐部当前人员情况。
- 用户可见的球队/球员事实、数据来源/赛季、样本风险、推断项和缺失信息都必须区分显示。没有可靠阵容数据时，Agent 需告知用户并请求必要材料或限定可分析范围，不能凭模型记忆伪装实时审查。
- 界面面向中文用户，新增和调整的用户可见中文统一使用简体中文。

## Testing Decisions

- 主要行为界面是多轮招募对话、能力评估与推荐结果、浏览器计划存储模块；不以 LangGraph 内部节点作为外部验证面。
- 对话测试通过 Fastify HTTP 案件接口注入确定性规划器和球员数据仓库，覆盖工具调查、追问、同案恢复、证据报告和数据限制。
- 前端 API 测试覆盖对话 endpoint 路径、请求体和共享响应契约；计划存储测试覆盖对话/报告保存、最近快照更新、版本迁移、删除和损坏数据保护。
- 候选比较测试覆盖最多三名球员的选择上限、指标行与候选人列的对应关系，以及缺失维度的显式空值。每位推荐候选会返回完整的已计算证据；Agent 单独标记本轮重点引用的指标，不能因未被引用就显示成无数据。
- 测试只断言用户可见结果和接口合同，不断言节点调用顺序、内部状态字段或模型提示词细节。
- 自动化验证不得依赖真实 LLM 密钥或在线 StatsBomb 服务；使用确定性适配器和固定数据样本。
- 已使用仓库现有 Node 测试运行器新增并运行上述行为测试。

## Out of Scope

- 账号、云端同步或服务端保存用户的招募计划。
- 自动定时任务、自动通知、无人值守的引援决策。
- 非欧身份、工作许可、联赛/欧战注册细则与财务合规推断。
- 首版不预测薪资、合同谈判、伤病史或交易成功率；用户明确提供的预算偏好可作为范围输入，但不据此声称掌握俱乐部真实预算。
- 对球员未来表现或转会成功率作预测；将启发式评分包装成经过验证的模型。
- 复制 Football Manager 的官方职责目录、界面或专有评分权重。
- 自动调用 football-data.org 并通过姓名猜测外部球员 ID 映射。

## Further Notes

- RAG/Agent 评测方向已确定；具体标注样本、评测问题、检索指标阈值和首批准入来源清单待实现前按真实语料范围落定。
- 当前只准入 PLOS ONE 一篇 CC BY 足球表现分析方法论文；没有可用的具名球员报告来源。PLOS API 元数据发现、登记 DOI 正文采集、许可检查和本地 JSON 入库命令已实现；通用网页搜索、来源刷新/删除和许可核查界面仍未实现。球员报告检索必须指定球员实体，只有实体元数据匹配的片段才进入模型上下文。
- multilingual E5 q8 是未标定的初选模型；最终 embedding 模型需用项目标注集评测后固定，切换模型时必须重建向量。
- 初始能力画像、指标口径和比较基准必须严格限制在数据源可观测字段范围。推荐排序的离线评估方案仍待定义；在没有验证依据前，不应把权重或总分表述成客观能力等级。
- `ChatOpenAI` 与结构化输出的官方集成说明：[LangChain OpenAI integration](https://docs.langchain.com/oss/javascript/integrations/chat/openai)。
