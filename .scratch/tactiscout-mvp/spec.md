# TactiScout 可演示球探 MVP

Status: ready-for-agent
Labels: ready-for-agent

## Problem Statement

TactiScout 当前能从结构化字段生成一份候选名单，但自然语言需求只靠简单关键词识别；招募需求不能保存，候选人也不能并排比较。战术适配分是启发式结果，用户需要看到它依据哪些统计、样本是否足够、哪些维度没有数据，避免把演示结果误当成可靠预测。

## Solution

把工作台扩展成一个完整的招募计划流程：用户用自然语言描述需求，服务端将其解析成可编辑的结构化草稿；用户核对并确认后运行 LangGraph 球探流程。结果给出透明排序、职责阶段适配、统计证据和风险。用户可以保存计划和最近结果快照，在候选名单中选 2–3 人比较，并手动重新分析。第一版无需账号或数据库，招募计划保存在浏览器 localStorage。

LLM 只负责把自然语言映射到有限、已知的招募字段。球员筛选、指标计算、职责模板评分和证据完整度由确定性代码计算。LLM 不得编造球员事实、统计或缺失的球队与位置要求。

## User Stories

1. 作为球探，我想用自然语言描述目标球队、位置、年龄和战术要求，以便快速建立招募计划。
2. 作为球探，我想在运行分析前看到模型识别出的每个字段，以便发现并修正误解。
3. 作为球探，如果目标球队或位置没有说清，我想看到缺失项并补齐，以便模型不会沿用旧表单值或猜测。
4. 作为没有配置模型密钥的用户，我仍想用结构化表单建立需求并运行球探流程。
5. 作为用户，我想将同一候选人的有球职责和无球职责分开描述，以便表达更具体的战术任务。
6. 作为用户，我想看到每种职责使用了哪些可观测指标，以便理解其适配结果。
7. 作为用户，当开放数据没有覆盖某种职责属性时，我想看到明确的数据缺口，以便该属性不被伪装成已评分。
8. 作为用户，我想按位置、年龄和确认过的战术画像筛选候选球员，以便得到符合基本条件的候选名单。
9. 作为用户，我想查看每名候选人的每 90 分钟数据、出场样本、来源、赛季和位置，以便判断比较是否公平。
10. 作为用户，我想查看每项适配信号背后的统计依据和风险，以便区分数据事实与启发式解释。
11. 作为用户，我想知道证据完整度反映的是数据覆盖和样本情况，以便不把它理解为推荐正确概率。
12. 作为用户，我想按可解释规则查看候选人排序，以便知道排名来自哪些指标。
13. 作为用户，我想选择 2–3 名候选人并排比较关键统计、有球与无球适配、样本和风险，以便进一步评估差异。
14. 作为用户，我想把一次需求和最近的分析结果保存成招募计划，以便离开页面后继续查看。
15. 作为用户，我想重命名、编辑和删除自己的招募计划，以便整理本地工作空间。
16. 作为用户，我想手动重新分析一个已保存计划，以便获取当前数据对应的新结果。
17. 作为用户，我想在重新分析前继续查看上一份分析快照，并在完成后用新快照替换，以便刷新失败时不丢失旧结果。
18. 作为演示者，我想在没有本地真实数据集时使用标明为虚构的演示数据，以便完整展示交互流程。
19. 作为使用 StatsBomb Open Data 的用户，我想看到数据集范围、统计代理指标和年龄限制，以便理解结果的适用边界。
20. 作为用户，我想用简体中文完成主要工作流，以便界面语言一致、易读。

## Implementation Decisions

- 保持全 TypeScript：React 工作台、Fastify 服务端和 LangGraph 分析工作流。
- 增加自然语言解析入口。解析返回未确认的需求草稿、缺失必填项和需要用户注意的字段；只有通过用户编辑和确认后，才调用现有球探入口。
- 使用 `@langchain/openai` 的 `ChatOpenAI` 适配兼容 OpenAI 的模型服务，使用 Zod 结构化输出。服务端从环境变量读取模型名称、可选兼容服务地址和密钥；密钥不得发送到浏览器。具体模型名由本地配置决定。
- 不配置模型密钥或模型调用不可用时，结构化表单仍可完整工作。模型解析不能被静默替换成不透明猜测；界面应保留用户原始文字、说明不可解析原因并允许手工补齐。
- 结构化草稿允许球队、位置等必填字段暂缺；用户补齐并确认之前不得运行筛选。不得把之前的表单值隐式当成新招募计划的解析结果。
- 使用少量 TactiScout 自定义职责模板，分成有球与无球职责。第一批模板为有球：推进持球者、控球组织者、机会创造者；无球：积极施压者、防守破坏者。适配公式分别为 `min(100, 2×带球/90 + 8×长传/90)`、传球成功率、`min(100, 15×射门助攻/90 + 8×助攻/90)`、`min(100, 4.5×施压/90)`、`min(100, 8×(抢断+拦截)/90)`。模板、底层指标与代理属性必须在界面中可见；无数据维度显示“暂无数据”且不影响分数。
- 数值筛选、每 90 分钟统计、职责适配、排序、样本提示和证据完整度使用确定性代码。总体适配是用户所选职责分数的算术平均；分钟数不混入适配分，只单独作为样本风险和证据覆盖提示。推荐理由必须引用实际统计或明确说明是代理指标。不得把尚未校准的分数转换成“推荐 / 接近 / 不匹配”等阈值等级。
- 证据完整度是数据可用性与样本覆盖的说明，不是推荐正确率。对外字段和文案应使用领域词汇 `证据完整度`，避免称为“推荐置信度”。
- 比较视图只接受当前候选名单中用户明确选择的 2–3 人，并使用相同统计口径展示关键指标、有球职责、无球职责、分钟样本、数据可用性和风险。
- 每份招募计划包括可编辑的需求、计划名称、创建/更新时间，以及最近一次分析快照。快照包含候选名单、排序、证据、风险、数据来源和分析时间。计划支持创建、打开、编辑、重命名、删除和手动重新分析；重新分析成功后才替换快照。
- 招募计划和快照只保存在浏览器 localStorage；第一版没有用户账号、跨设备同步或服务端数据库。存储内容应带版本标记，以便后续格式变化可以显式处理。
- 主要真实数据来源为本地 StatsBomb Open Data；没有数据集时继续使用显著标记的虚构演示数据。年龄可使用与外部球员 ID 明确对齐的人口信息 sidecar，并展示来源和核实时间；不做姓名模糊匹配。
- 页面必须持续展示数据来源、样本风险、未知年龄以及推进等代理指标的限制。目标球队名称仍是计划上下文，不表示系统已掌握该俱乐部的真实预算、合同、伤病或战术模型。
- 界面面向中文用户，新增和调整的用户可见中文统一使用简体中文。

## Testing Decisions

- 主要行为界面是需求解析入口、确认后调用的球探入口和浏览器计划存储模块；不以 LangGraph 内部节点作为外部验证面。
- 如果后续获准添加自动化测试，解析行为应通过注入的模型适配器覆盖完整与缺失字段；球探行为应通过 HTTP 契约验证；计划行为应通过可替换的浏览器存储适配器验证保存、重载、更新和删除；比较行为应验证用户选择和展示的 2–3 个候选人一致。
- 测试只断言用户可见结果和接口合同，不断言节点调用顺序、内部状态字段或模型提示词细节。
- 自动化验证不得依赖真实 LLM 密钥或在线 StatsBomb 服务；使用确定性适配器和固定数据样本。
- 本规格记录验证 seam，但当前实现阶段不新增或运行测试，除非用户明确要求测试或验证。
- 仓库当前没有可沿用的测试文件或测试惯例；新增测试时需先核对项目运行器和既有约定。

## Out of Scope

- 账号、服务端数据库、跨浏览器或跨设备同步。
- 自动定时任务、自动通知、无人值守的引援决策。
- 预算、薪资、合同、伤病史、经纪人或转会可行性判断。
- 对球员未来表现或转会成功率作预测；将启发式评分包装成经过验证的模型。
- 复制 Football Manager 的官方职责目录、界面或专有评分权重。
- 自动调用 football-data.org 并通过姓名猜测外部球员 ID 映射。

## Further Notes

- 排序效果的离线评估数据集和指标仍未决定；在职责模板与可用统计字段落定后单独处理。
- 初始职责模板和权重必须严格限制在 StatsBomb 当前可观测字段范围。后续若需要定位或球员角色模型，应先定义独立、可复现的评估方案。
- `ChatOpenAI` 与结构化输出的官方集成说明：[LangChain OpenAI integration](https://docs.langchain.com/oss/javascript/integrations/chat/openai)。
